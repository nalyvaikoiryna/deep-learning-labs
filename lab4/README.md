# Лабораторна робота №4. FP32 проти INT8

Мета роботи — експортувати ResNet18 із ЛР3 у формат ONNX і дослідити, як статична квантизація в INT8 впливає на якість класифікації, затримку на CPU та розмір файла моделі.

## Вихідні дані

Використано `lab3_model.pt`, `split.csv` і набір Intel Image Classification із ЛР3. Для перевірки поділу підраховано зображення та підсумовано числові частини їхніх імен. Обидві величини збіглися з контрольними числами.

| Частина | Кількість зображень | Сума числових імен |
| --- | ---: | ---: |
| `train` | 1200 | 11 993 084 |
| `test` | 1502 | 33 351 444 |

Для кожного тестового зображення виконано перетворення в RGB, зміну розміру до 160 × 160, перетворення на тензор і нормалізацію зі статистиками ImageNet. Зображення оброблено пакетами по 64 у порядку рядків `test` у `split.csv`.

## 1. Експорт FP32 і перевірка відповідності

Ваги з чекпойнта завантажено на CPU в ResNet18 із шістьма виходами. Експорт виконано в режимі `eval()` за допомогою `torch.onnx.export` із `dynamo=False` та opset 17. У тензорів `input` і `logits` перша вісь змінна. Сесію ONNX Runtime створено з `CPUExecutionProvider` та значенням 1 для `intra_op_num_threads` і `inter_op_num_threads`.

Максимальну абсолютну різницю обчислено поелементно. Для кожного з 1502 зображень віднімали логіти PyTorch та ONNX FP32 для відповідних шести класів, брали модулі різниць і знаходили максимум серед усіх 9012 значень.

| Показник | Результат |
| --- | ---: |
| Максимальна абсолютна різниця логітів | 0,000076 |
| Частка збігів передбаченого класу | 1,000000 |
| Macro-F1 PyTorch на `test` | 0,887931 |
| Macro-F1 ONNX FP32 на `test` | 0,887931 |
| Кількість вузлів `Conv` | 20 |
| Кількість вузлів `BatchNormalization` | 0 |
| Час експорту, с | 0,273 |

Різниця логітів **0,000076 < 0,001**, тому числовий критерій перевірки пройдено. Передбачені класи збіглися для всіх 1502 тестових зображень. Macro-F1 обох варіантів збігається з результатом на `test` у ЛР3 (0,887931). Вузли підраховано за `op_type` у збереженому ONNX-графі; їхня кількість відповідає контрольним значенням. Під час експорту в режимі `eval()` пакетна нормалізація зливається зі згортками. Час експорту виміряно окремо, без перевірки графа та оцінювання на `test`.

## 2. Калібрування й квантизація

Калібрувальну вибірку сформовано лише з `train`: 1200 рядків відсортовано за іменем файла як за рядком, потім узято позиції `np.random.default_rng(0).permutation(1200)[:200]`. Перевірено контрольні числа: 200 зображень, сума числових імен файлів 1 921 470; за класами — `buildings` 40, `forest` 35, `glacier` 36, `mountain` 33, `sea` 29, `street` 27. `test` для калібрування не використовується.

Калібрувальний читач подає по одному зображенню `float32` форми `(1, 3, 160, 160)` і завершується після 200 зображень. Граф `lab4_fp32_preprocessed.onnx` створюємо через `quant_pre_process` із `skip_symbolic_shape=True` та перевіряємо `onnx.checker.check_model`.

Фіксовані параметри статичної квантизації: `QuantFormat.QDQ`, активації `QuantType.QUInt8`, ваги `QuantType.QInt8`, `per_channel=True`, калібрування `CalibrationMethod.MinMax`; решта аргументів `quantize_static` — за замовчуванням.

Створено `lab4_int8.onnx`; перевірка `onnx.checker.check_model` пройшла. В останньому повному запуску квантизація з калібруванням і записом файла тривала 3,218 с; підготовка графа та перевірка файла не входили до цього часу. Час залежить від середовища запуску.

## 3. Якість FP32 та INT8

| Варіант | Macro-F1 | Accuracy | Згода з FP32 | b | c | Δacc ± SE |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| FP32 | 0,887931 | 0,885486 | 1 | 0 | 0 | — |
| INT8 | 0,890501 | 0,888149 | 0,994674 | 6 | 2 | +0,002663 ± 0,001883 |
| INT8 per-tensor | 0,882378 | 0,880160 | 0,990679 | 3 | 11 | −0,005326 ± 0,002491 |

На всіх 1502 зображеннях `test` INT8 правильно класифікувала шість зображень, на яких FP32 помилилася (`b = 6`); FP32 правильно класифікувала два зображення, на яких INT8 помилилася (`c = 2`). Різниця accuracy становить `(b − c) / 1502 = +0,002663`. За правилом роботи `|b − c| = 4 ≤ 2√(b + c) = 5,656854`, тому різниця не відрізняється від шуму. Її парна стандартна похибка дорівнює 0,001883, а похибка accuracy однієї FP32-моделі `√(p(1−p)/1502)` — 0,008216, приблизно у 4,36 раза більша. Парне порівняння точніше, бо обидві моделі оцінено на тих самих зображеннях і розходження в правильності є лише для восьми з них.

## 4. Дослід із потензорними вагами

Для кожного з 20 вузлів `Conv` у `lab4_fp32.onnx` ваги взято з ініціалізатора за другим входом вузла. Для вихідного каналу обчислено `α_c = max |w|`, а для згортки — `r = max_c α_c / median_c α_c`.

| Згортка | `r` |
| --- | ---: |
| `/conv1/Conv` | 6,6683 |
| `/layer3/layer3.1/conv2/Conv` | 5,8957 |
| `/layer3/layer3.0/downsample/downsample.0/Conv` | 4,9206 |

Медіана `r` за 20 згортками — **3,6546**; для медіанної згортки це відповідає `log₂(r) ≈ 1,87` біта. Ці числа обчислено з ваг саме цього чекпойнта; у прикладі умови наведено медіану 3,44.

**Прогноз до запуску `per_channel=False`.** Очікую нижчої згоди з FP32 через грубіший спільний масштаб ваг; помітного погіршення якості не прогнозую. Підстава — медіанне `r = 3,6546` показує втрату роздільності для частини каналів, але саме по собі не визначає, скільки класифікацій зміниться.

**Результат і зіставлення з прогнозом.** Модель `lab4_int8_per_tensor.onnx` побудовано на тій самій калібрувальній вибірці й з тими самими параметрами, окрім `per_channel=False`. Згода з FP32 знизилася з 0,994674 до 0,990679, отже прогноз щодо згоди справдився. Macro-F1 знизився з 0,890501 до 0,882378 порівняно з поканальним INT8, тобто на 0,008123; прогноз щодо відсутності помітного погіршення не справдився. Для потензорної моделі `b = 3`, `c = 11`, тому `Δacc = −0,005326 ± 0,002491`. За парним правилом пункту 3 `|b − c| = 8 > 2√(b + c) = 7,483315`: погіршення accuracy відрізняється від шуму за цим правилом. Воно застосовується до accuracy, а не є оцінкою похибки macro-F1.

Початковий прогноз вище залишено без змін. Формально правило пункту 3 перевіряє зміну accuracy за `b` і `c`; для macro-F1 воно не задає похибку. Тому висновок про вихід за межі шуму стосується accuracy, а зміну macro-F1 наведено як спостережувану різницю.

Згода з FP32 реагує на кожну зміну передбаченого класу. Macro-F1 усереднює показники шести класів, а `b − c` показує чисту зміну кількості правильних відповідей: покращення можуть компенсувати частину погіршень. Тут три покращені випадки компенсували три з одинадцяти погіршених, тож чиста втрата становить вісім правильних відповідей.

## 5. Затримка та розмір моделей

| Варіант | Розмір файла, МБ | p50, мс | p95, мс | p50 за раундами, мс |
| --- | ---: | ---: | ---: | --- |
| FP32 | 44,71 | 24,541 | 24,945 | 24,545; 24,543; 24,534 |
| INT8 | 11,30 | 6,190 | 6,249 | 6,188; 6,191; 6,188 |

Розміри отримано з розмірів збережених файлів у байтах діленням на 10⁶: FP32 — 44 708 866 байтів, INT8 — 11 297 049 байтів. Файл INT8 менший у **3,958 раза**.

Для затримки використовуємо перше зображення `test` у порядку `split.csv`, підготовлене до `float32` форми `(1, 3, 160, 160)` до запуску таймера. Сесії FP32 і поканального INT8 створюються заздалегідь. У кожному з трьох раундів спершу FP32, потім INT8 отримують по 20 прогрівальних викликів і 100 вимірів. Один вимір охоплює лише `sess.run` між двома викликами `time.perf_counter()`. Загальні p50 і p95 беруться з усіх 300 вимірів кожного варіанта; окремо записуємо p50 кожного раунду. Прискорення рахуємо як `p50_FP32 / p50_INT8`; зміну затримки вважаємо виміряною, якщо інтервали від мінімального до максимального p50 за раундами не перетинаються.

Виміряне прискорення за p50 становить **24,541 / 6,190 = 3,965 раза**; за p95 — **3,992 раза**. Інтервали p50 за раундами: FP32 — **[24,534; 24,545] мс**, INT8 — **[6,188; 6,191] мс**. Вони не перетинаються, тому за правилом роботи зміну затримки вважаємо виміряною.

Середовище вимірювання: Apple M1, macOS 14.2.1, Python 3.12.2, PyTorch 2.15.0, torchvision 0.29.2, ONNX 1.23.2, ONNX Runtime 1.32.0; `CPUExecutionProvider`, один внутрішній та один міжоператорний потік, пакет розміру 1. Під час запуску ноутбук був підключений до живлення, важкі програми були закриті. У `lab4_results.json` збережено всі 300 вимірів для кожного варіанта.

## 6. Висновок

На Apple M1 поканальна INT8-модель менша за FP32 у **3,958 раза** (11,30 проти 44,71 МБ). Її p50 нижча у **3,965 раза** (6,190 проти 24,541 мс), а p95 — у **3,992 раза** (6,249 проти 24,945 мс). Інтервали p50 за трьома раундами не перетинаються, тому зменшення затримки виміряне за правилом пункту 5.

На 1502 тих самих тестових зображеннях показники поканальної INT8-моделі не знизилися: macro-F1 становить **0,890501** проти **0,887931** у FP32, згода передбачених класів — **0,994674**. Різниця accuracy **+0,002663 ± 0,001883** при `b = 6`, `c = 2` не виходить за межі шуму за парним правилом пункту 3. Потензорний варіант із пункту 4 дав нижчі macro-F1 **0,882378** і згоду **0,990679**, тому для цієї задачі обираємо поканальну квантизацію.

Прискорення **3,965 раза** майже дорівнює зменшенню розміру файла **3,958 раза**. За моделлю даху скорочення обсягу ваг зменшує потребу в пропускній здатності пам’яті, а ефективні INT8-операції можуть підвищувати обчислювальну межу. CPU Apple M1 має цілочисельні векторні операції Neon у своїх ядрах; у цьому запуску задано `CPUExecutionProvider`, тому окремий Neural Engine не використовувався. Самої близькості двох коефіцієнтів недостатньо, щоб довести, чи обмежувала виконання пам’ять або обчислення і які саме інструкції застосував ONNX Runtime: для цього потрібне профілювання. [Посібник Apple щодо CPU](https://developer.apple.com/documentation/Apple-Silicon/cpu-optimization-guide), [опис Neon від Arm](https://developer.arm.com/documentation/101028/0009/Advanced-SIMD--Neon--intrinsics), [документація ONNX Runtime щодо квантизації](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html).

За отриманими результатами поканальна INT8-модель придатна для цієї задачі на цьому ноутбуці: вона істотно менша й швидша, а зміна accuracy на тесті не відрізняється від шуму за заданим правилом.
